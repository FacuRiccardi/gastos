# Demo environment — design

## Intent

The owner wants to show the app to coworkers and friends. They should be able to open a link, get into the
app with one click, and use **everything the app does**, with believable but fictional data, without any
risk to the real household data and without any chance of a bill.

Why now: the app is feature-rich enough (home, cards, categories, budget, balance, cap alerts) that showing
it beats describing it.

## What the visitors get

A hosted copy of the web app, in Spanish like the real one, with:

- A login screen with a single **"Entrar a la demo"** button. No Google account, no password to type.
- **A few purchases still to categorize**, so people can try the Categorías flow (categorize a purchase, see
  the merchant dictionary grow, see the orange "purchases without a category" alert on Inicio shrink).
- **Several closed statement periods** (at least three per account) so Gastos, Tarjetas (cycles) and Balance
  show real history, including the month-by-month history table in Balance.
- **One statement period in progress** that shows on Inicio with its progress bar against the monthly
  spending cap, "Más datos" (category shares) and its list of purchases. While the last closed period has
  not fallen due yet Inicio also shows it; the seed data should be built so that, on the day it is loaded,
  Inicio shows both.
- A **cap alert** on Inicio (e.g. "Superaste el 50% de tu tope") so that banner can be seen.
- Incomes (ARS and USD, with exchange rates), fixed expenses, savings and a spending cap loaded, so Presupuesto
  and Balance are not empty.
- Everyone shares the same demo user and the same data; visitors can edit anything the real app lets them edit.

## Goals

1. **Isolation from production.** The demo lives in its own Firebase project. It shares no database, no auth
   users and no config with the real one.
2. **Zero cost by construction.** The demo project stays on the free Spark plan with **no billing account
   linked, ever**. If its free quota is exhausted (by abuse or popularity) the demo stops working until the
   quota resets; nothing is charged. This is accepted.
3. **One-command reset.** One script puts the demo back to its initial state (wipe + reseed), because
   visitors will change and break things. The same script is how the demo is refreshed when its dates get
   old (see "Dates").
4. **Fictional data only.** Generated by code committed in the repo. No real merchants tied to the owner, no
   real card digits, no real names, nothing derived from the production dump.
5. **Production untouched.** Production behaviour, production deploy (`web:deploy`) and production data are
   unchanged. The demo-only UI shows up only in the demo build.

## Non-goals

- Automatic ingestion of new purchases from Gmail. The ingestion functions (Pub/Sub, Cloud Run, Scheduler,
  Terraform) are **not** deployed to the demo project. The demo has no new purchases arriving.
- A separate sandbox per visitor.
- Protecting the link (password, App Check, allow-lists). The link is open on purpose; the data is fake.
- Scheduled / automatic reset. Reset is run by hand when needed.
- Push notifications (FCM) in the demo. The demo build uses the same inert push API the emulator mode uses.
- Making the demo reflect the installments feature (`2026-11-04-installments-design.md`) — that is not
  built yet. If it ships, extending the seed is a separate task.
- A tool to inject a "new purchase arriving" during a live demo. Possible later.

## Anti-goals (a failure even if it technically works)

- The demo project ever having a billing account linked, or any step in this work requiring one.
- The reset (or seed, or deploy) script ever running against the **production** project: a wiped production
  database is the worst outcome of this work. The scripts must refuse unless pointed at a project that is
  positively identified as the demo (see "Safety guards").
- Real household data (or the private `emulator-data/` dump) reaching the demo project or the repo.
- The demo login button, demo credentials or demo badge appearing in the production build.
- A demo that looks empty or stale on first open (nothing to categorize, no history, nothing in progress).

## Decisions already made (by the owner)

- Separate Firebase project on Spark, no billing, kept apart from production.
- One shared demo user for everyone; a reset script restores the data.
- Open link with an "Entrar a la demo" button (no password handed out per person).
- No Gmail ingestion in the demo.
- Data contents as listed under "What the visitors get": a few uncategorized purchases, a couple of closed
  statements for history, one in progress.

## Design (the builder's plan should follow this; items marked *my call* are proposals the owner can reverse)

### Demo build of the web app

- A build mode (e.g. `vite build --mode demo`, with a git-ignored/untracked `web/.env.demo` or equivalent for
  the demo project's Firebase web config and the demo user's email and password). Firebase web config and the
  demo password are not secrets here: they end up in the public bundle by design, and the account only holds
  fake data.
- In that mode the login screen shows the "Entrar a la demo" button, which signs in with email + password to
  the shared demo user through a new method on `AuthApi` (alongside `signInWithGoogle`), so components stay
  testable with a fake as today. The Google button is not shown in the demo build. *(my call)*
- In that mode push uses the inert push API (as the emulator mode does today).
- *(my call)* A small, unobtrusive "Demo · datos ficticios" badge/label so visitors know the data is fake and
  shared. Text in `strings.ts`, like all UI text.
- `VITE_OWNERS` for the demo build are fictional names, matching the holders/owners in the seed.
- The production build (default mode) must be byte-for-byte unaffected in behaviour: no demo button, no badge.

### Seed / reset script

- A new script (e.g. `scripts/demo-seed.js`, `npm run demo:reset`) that **generates** the documents in code
  for all the collections the app uses (`expenses`, `categories`, `accounts`, `cards`, `cycles`,
  `merchantCategories`, `fixedTypes`, `fixedExpenses`, `exchangeRates`, `spendingCaps`, `incomes`,
  `savings`, plus `capAlerts`), following the data model in `README.md` (document IDs, field shapes,
  `YYYY-MM-DD` strings for calendar dates, `Timestamp` for `purchaseDate`/`receivedAt`).
- It also creates (or updates) the demo auth user (email/password from config) and sets the custom claim
  `household: true`, which the Firestore rules require. Same rules file as production is deployed to the
  demo project.
- It wipes the demo collections (including `capAlerts` and its `dismissals`, and `pushTokens`) before seeding,
  so running it twice, or after visitors changed things, always yields the same initial state.
- **Dates are relative to the day it runs.** Closed cycles, the in-progress period, purchase dates, fixed
  expense months, exchange rates and caps are all computed from "today" so that "closed history + one in
  progress (+ the last closed still not due)" is true on the day of loading. Consequence: when the dates
  get old (about a month later), run the reset again to refresh. This should be written in the runbook.
- Data shape (sizes are guidance, the builder may adjust):
  - 2 accounts with different closing days, 2–3 credit cards (one extra holder), different holders
    (fictional first names), plus one debit card so "debit is left out of the totals" can be seen.
  - Roughly 4 months of purchases, ~40–70, in plausible Argentine-style amounts, with a handful of categories
    with distinct colours, and a merchant → category dictionary covering most merchants.
  - **3–5 purchases from merchants not in the dictionary and with no `categoryId`** in the current/recent
    period, so there is something to categorize. One rejected purchase (shown but not counted).
  - Fixed expenses and incomes loaded for the past months and the current one so Presupuesto/Balance are
    complete *(my call: the red "missing fixed expenses/incomes" alerts are NOT shown in the initial state;
    only the orange "purchases without a category" one is, since that is the one the demo is built around)*.
  - A cap alert doc for the current month so the Inicio banner is visible (the existing
    `scripts/seed-emulator.js` already does the same for the emulator).
- Merchant names should be invented (or generic, e.g. "Supermercado del Barrio"), not tied to the owner.
- The data generation should be a pure function of (today, seed) so it can be unit-tested for the invariants
  above (dates in order, closed cycles have both dates, at least N uncategorized, no purchase in the future,
  …). Use a fixed pseudo-random seed so the content is stable between runs, only shifted in time.

### Safety guards

- Seed/reset and deploy scripts take the project ID explicitly (flag or env), never from an ambient default
  (`.firebaserc` and `gcloud` defaults point at production).
- The reset script refuses to wipe a project unless it is positively the demo: *(my call)* a marker document
  (e.g. `demoMarker/demo`, not readable or writable from browsers because it has no rule) must exist, or the
  database must be completely empty (first run, which then creates the marker). A project that has data and
  no marker is refused, with a clear message. The builder may choose another mechanism if it is at least as
  hard to get wrong.
- The demo deploy script builds in demo mode and deploys **only Hosting and Firestore rules** to the demo
  project, with `--project` passed explicitly.
- Neither the seed nor the deploy may use or read `emulator-data/`.

### Documentation

- A "Demo" section in `RUNBOOK.md` (and a short mention in `README.md`) with the one-time setup, in plain
  steps the owner can follow: create a new Firebase project, stay on Spark and do **not** link billing, enable
  Authentication → Email/Password, create the Firestore database, register a web app and copy its config into
  the demo env file, deploy, run the reset. Plus how to reset, how to refresh stale dates, and what to do if
  the free quota runs out (wait for the daily reset, or reset the data).

## Constraints and known unknowns

- The owner's machine is Windows; scripts must work there (the repo already uses Node ESM scripts and
  PowerShell/Git Bash in docs).
- Firebase Admin SDK access to the demo project from the owner's machine: expected to work with
  `gcloud auth application-default login` as the project owner. **To be verified** during implementation that
  this works on a Spark project with no billing (e.g. no quota-project error); if it needs a service-account
  key, keep that key out of the repo (git-ignored) and document it.
- With Email/Password enabled, anyone with the public API key can technically create *other* accounts in the
  demo project. Those accounts have no `household` claim, so the Firestore rules give them no access.
  Accepted; nothing to build.
- Visitors share state: one person's change is seen by the others. Expected and accepted.
- The Firestore rules already restrict browser writes to specific collections/fields, so a visitor cannot
  do more than the real app allows; the worst a visitor can do is change or delete the fictional data.

## Resolved questions (from the pre-build review)

Answered by the code (checked):

- **The web app needs nothing from the backend.** It talks only to Firestore and Auth (no Cloud Functions
  calls). The cap-alert banner reads `capAlerts/{month}` (`lastLevel`, `total`, `cap`) and writes only the
  per-user dismissal (`capAlerts/{month}/dismissals/{uid}`), so seeding that document is enough. The only
  other backend-fed piece is FCM push, which is inert in the demo.

Settled as my calls (the owner can reverse them):

- **Hosting.** Firebase Hosting on Spark is fine. Reuse the same `firebase.json`; the demo deploy always
  passes `--project <demo-id>` explicitly and the script refuses to run if the target equals the default
  project in `.firebaserc` (production) or if the project ID is not the configured demo one. No second
  hosting config file is needed.
- **Dates guarantee.** Must hold for **both** accounts and for **any** day of the year, including the 29th–31st
  (clamp closing days to the month length). Suggested construction: each account's last closing date is a few
  days before today (different offsets per account, e.g. 4 and 9 days), due date = closing + ~12 days
  (so it is still in the future today), previous closings step back one month at a time. Unit-test the
  invariants for every day of a year. "Due" means the cycle's `dueDate` (README data model: `cycles`).
- **Cap alert consistency.** The in-progress period's total must be consistent with the cap and the alert:
  choose the cap so the in-progress spend is about 50–70% of it, and write `capAlerts` with `lastLevel: 50`
  and `total` equal to the amount at the time it was crossed, `cap` equal to the seeded cap. The banner and
  the progress bar must not contradict each other.
- **Project identification.** In addition to the marker document: the script asserts that the Admin SDK's
  effective project ID equals the `--project` flag (not an ambient default). An empty project on first run is
  seeded and gets the marker; that is accepted.
- **Demo credentials.** One untracked file holds both the web build's demo values (`VITE_*`, including the demo
  email/password) and what the seed script needs (it reads the same file), so the password is defined once.

## Left to the builder

- Exact names of scripts, env files and npm scripts.
- Exact fictional merchants, categories, names, amounts and the pseudo-random generator.
- How the demo flag is wired (Vite mode vs. an env variable) as long as production is unaffected.
- Exact wording of the Spanish strings (button, badge, errors) in `strings.ts`.
- Test layout, following the existing style (Vitest; fakes for `AuthApi`).

## Testing expectations

- Web: a test that the demo login button appears only when the demo flag is on, and calls the new demo
  sign-in; and that it is absent otherwise (production behaviour unchanged). Existing tests keep passing.
- Seed: unit tests of the pure generator for the invariants above.
- Existing security-rules tests are unaffected (rules are not changed).
- Manual: reset the demo, open the link, click the button, walk through each tab; categorize a purchase;
  run the reset again and confirm it returns to the initial state.
